## 2. من أين جاء الوقت · Where the time was

`/dashboard/home` قبل/بعد، بجلسة واحدة دافئة على نفس البيانات:

| المقياس | قبل | بعد |
| --- | --- | --- |
| جمل SQL لكل طلب | **60** | **10** |
| زمن الطلب (دافئ، داخل العملية) | 89.8 ms | 47.9 ms |
| زمن المسار عبر HTTP (متوسط 5) | 146.9 ms | ~54 ms |

تفصيل الـ50 جملة الزائدة (من `before_cursor_execute`):

| التكرار | الجملة | السبب |
| --- | --- | --- |
| 9× | `roles→permissions`, `user_scopes`, `client_portal_users` | شجرة صلاحيات المسؤول تُقرأ لكل صف طلب |
| 6× | `document_requirements` | علاقة `InsuranceType` من نوع `selectin` تُحمَّل لكل نوع تأمين |
| 3× | `client_contacts` | جهات اتصال العميل — لا تُعرض في صفود اللوحة |
| 8× | `count(*)` منفصلة | KPI row: ستة عدّادات ومتوسطان، كل واحد رحلة ذهاب وعودة |

الإصلاح: سياسة تحميل واحدة عامة (`requests_repo.list_options()`) يستخدمها **الجدول واللوحة**، ودمج عدّادات
`kpis()` و«اليوم» في استعلام واحد لكل منهما — بنفس الشروط والمعادلات، بلا تغيير في أي رقم.

## 3. فهرس الأقساط · The one index

البوابة: «اليوم» يقرأ أقساطًا مستحقة خلال 14 يومًا مرتبة بالتاريخ. القياس على 36,042 قسطًا، نفس الجلسة،
نفس الاستعلام، بإسقاط الفهرس وإعادة إنشائه:

| | قائمة (وسيط/أقصى) | عدّ (وسيط/أقصى) | الخطة |
| --- | --- | --- | --- |
| بلا `ix_installments_due` | 3.25 / 6.12 ms | 3.07 / 3.67 ms | `Seq Scan on installments` (36,042 صفًا) + `top-N heapsort` |
| مع `ix_installments_due` | **0.19 / 1.14 ms** | **0.90 / 1.10 ms** | `Index Scan using ix_installments_due` |

**17.1×** للقائمة و**3.4×** للعدّ. الفهرس الوحيد الذي أُضيف؛ بقية المسارات تخدمها فهارس موجودة (أدناه).

### خطط المسارات الأخرى (بلا تغيير — `EXPLAIN (ANALYZE)`)

| الاستعلام | الخطة | الزمن |
| --- | --- | --- |
| `/requests?only_open` | `Index Scan Backward using ix_requests_last_activity` | 0.43 ms |
| عدّ الطلبات المفتوحة | `Index Only Scan using ix_requests_status_sla` | 0.94 ms |
| `/leads` | `Seq Scan + top-N heapsort` (2,000 صف) — فهرس `created_at` لا يغيّر الترتيب | 1.30 ms |
| `/leads/board` | `Index Scan using ix_leads_status` | 0.42 ms |
| `/clients` | `Seq Scan` (500 صفًا) — أصغر من أن يفيدها فهرس | 0.23 ms |

تفسير صريح: على 2,000 صفقة/500 عميل، `Seq Scan` **أسرع** من فهرس، فلا فهرس أُضيف. عند 100k صفقة يتغيّر القرار
ويحتاج قياسًا جديدًا — وهذا مكتوب في ADR-035 لا مُفترَضًا.

## 4. عامل واحد مقابل عاملين · 1 vs 2 workers


| --- | --- | --- | --- | --- | --- |
| عامل واحد (`:8024`) | 29.18 | 68 ms | 240 ms | 390 | 0 |
| **عاملان** (`:8021`) | **30.20** | **49 ms** | **200 ms** | 460 | 0 |

p50 أفضل **28%** وp95 أفضل **17%**، والإنتاجية +3.5% فقط. التفسير الصادق: على نواتين، العامل الثاني يضيف
تزامنًا في انتظار قاعدة البيانات ولا يضيف أنوية — الفائدة الحقيقية تظهر على 4+ أنوية (R13 قاس 52→86 rps على
آلة أكبر). لا نَدّعي أكثر من ذلك. الملفات: `docs/perf/raw/r15-mixed-{1,2}w_stats.csv`.
